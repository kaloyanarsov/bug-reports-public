SCS-1997

The Revision Bypass

A carrier marked an order "Picked Up" while a shipper's revision was still sitting unacknowledged. This walks the actual screen recording, frame by frame, to the one line of code that let it happen.

Bug 6 repos touched iOS + Android affected root cause: confirmed in source

In one line

The manual pickup/deliver path — on the server and in every app — was never wired into the "you can't touch this order until the revision is accepted" check that governs every other action.

Root cause — One rule, and the one path that skips it

The platform has a single authoritative rule for "can this order be touched right now." Load.is_api_allowed() returns False for every action except cancel/decline while a revision is pending:

Load.is_api_allowed() · platform-backend · epod/models.py:3955
if self.active_revision and action not in ('cancel', 'decline', 'broker_cancel', 'shipper_cancel'):
    return False   # pending revision → action refused

Every normal order action reaches that rule automatically, because it routes through the shared action machinery (perform_action → validate_api_allowed → is_api_allowed). The two manual status endpoints don't:

✓ Every other action

accept, edit, assign, mark-paid, archive… go through perform_action, which calls is_api_allowed and refuses while a revision is pending.

✗ manual_pickup / manual_deliver

Hand-written @action handlers that call get_object() and mutate the load directly. They check order status only — never is_api_allowed.

manual_pickup() · platform-backend · api/order_api.py:3691
def manual_pickup(self, request, pk=None):
    load = self.get_object()
    load.validate_not_parent_order(load)
    # ← no is_api_allowed() / active_revision check ever runs here
    if load.status != LoadStatus.assigned:
        raise ValidationError("Cannot pick up load which is not in assigned state.")
    # … proceeds to set status = picked_up and returns HTTP 200

The proposed fix is the guard that every other action already gets — the precedent is right there in the same file (accept_load, order_api.py:4583):

the fix — add to manual_pickup + manual_deliver

if load.active_revision:
    raise ValidationError("You need to accept or decline the pending "
                          "revision before you can update this order's status.")

Blast radius — The same gap repeats in every client

The backend fix is the authoritative one — it closes the hole for any caller. But the reason the carrier saw the button is that no client disables it either, even though each app already has the revision concept wired for other actions.

Log evidence — Why there is nothing in the logs

The failing call succeeds

This is a bug on a backend service, so the instinct is to grep Cloud Logging for the failure. There isn't one. The whole defect is that the request the carrier makes is accepted:

# what actually gets logged
POST /api/loads/RM5VO5/manual_pickup/ → 200 OK · no exception, no WARNING, no 5xx

# what a normal, correctly-guarded action would have logged
POST /api/loads/RM5VO5/<guarded>/ → 403 / 400 · is_api_allowed → refused

A 200 is indistinguishable from a legitimate pickup in the logs, so a log fan-out can neither confirm the bug nor find a root-cause line. The root cause was pinned in source instead (above), and the video is the behavioural proof.

Measuring real impact

Blast radius is a database question, not a log one. To size real customer impact, count orders that carry a manual-status flag while a revision was outstanding — e.g. loads with LoadFlags.manual_picked_up / manual_delivered whose revision history shows an active_revision unresolved at the time of the flag.

The repro order RM5VO5 / "Test DimitarShipper" is a test order, not a production incident.
